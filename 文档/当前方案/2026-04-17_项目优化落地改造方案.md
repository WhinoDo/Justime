# 项目优化落地改造方案（执行版）

> 日期：2026-04-17  
> 作用：将整改清单转化为可执行的改造步骤，明确每阶段目标、改动范围、风险与验收标准。

---

## 总体策略
- 先做“高风险、低耦合”的 P0 安全与正确性修复；
- 再做 P1 性能与架构收敛，避免边修边扩散；
- 最后做 P2 工程治理，降低后续维护成本。

---

## 阶段 A：安全与正确性兜底（P0）

### A1. 密钥与加密策略收敛
**目标**：避免不安全默认配置进入运行环境。  
**涉及文件**：
- `jushi_backend/app/core/config.py`
- `jushi_backend/app/services/encryption_service.py`

**实施要点**：
1. 增加启动期必填配置校验（JWT_SECRET、JWT_REFRESH_SECRET、ENCRYPTION_SECRET）。
2. 删除 `EncryptionService` 中默认弱密钥回退逻辑。
3. 区分“JWT 签名密钥”和“字段加密密钥”用途。

**风险点**：
- 旧环境变量不完整会导致启动失败（属于预期行为）。

**验收标准**：
- 缺失关键密钥时，服务拒绝启动并输出明确错误。
- 配置完整时，加解密流程可用。

---

### A2. 认证 Cookie 与 Token 行为统一
**目标**：登录、刷新、登出行为一致且具备生产安全属性。  
**涉及文件**：
- `jushi_backend/app/api/v1/endpoints/auth.py`

**实施要点**：
1. 统一 `set_cookie` 参数：`httponly/samesite/secure/path/max_age`。
2. 明确 refresh 令牌语义（避免“只有 access token 重新签发”的混乱行为）。
3. 清理登出行为，确保客户端 cookie 状态一致。

**风险点**：
- 前端现有读取逻辑可能依赖旧 token/cookie 行为。

**验收标准**：
- 登录后 cookie 设置符合预期；
- refresh 可稳定续期；
- logout 后鉴权失效。

---

### A3. 权限边界修复（禁止信任客户端 userId）
**目标**：消除基于 `userId` 参数的越权风险。  
**涉及文件**：
- `jushi_agent/src/app/api/calendar/events/route.ts`
- `jushi_agent/src/app/api/calendar/events/[id]/route.ts`
- `jushi_agent/src/app/api/documents/route.ts`
- 前端调用处（calendar/documents 页面）

**实施要点**：
1. 服务端从 token/session 解析当前用户，不接受客户端指定 userId。
2. 所有按资源 ID 查询/更新/删除必须附带 owner 条件。
3. 清理前端请求中的 userId 传参。

**风险点**：
- 调用契约变化会影响旧客户端。

**验收标准**：
- A 用户不能访问/修改 B 用户数据；
- 相关接口对匿名/非法会话返回正确状态码。

---

### A4. 错误处理契约统一
**目标**：前后端对错误处理可预测、可编排。  
**涉及文件**：
- `jushi_backend/app/api/v1/endpoints/knowledge.py`
- 其他存在 `try/except -> success:false` 的 endpoint

**实施要点**：
1. 业务失败按语义抛出 HTTPException（4xx/5xx）。
2. 保留业务字段时也要与 HTTP 状态码一致。
3. 补充统一错误返回结构（如 code/message/detail）。

**风险点**：
- 前端若仅依赖 `success` 字段，需要同步调整。

**验收标准**：
- 错误场景状态码语义正确；
- 前端无需针对同类错误写多套分支。

---

### A5. 快速正确性修复
**目标**：消除显式错误常量导致的潜在异常。  
**涉及文件**：
- `jushi_backend/app/core/validators.py`

**实施要点**：
- `status.HTTP_400_REQUEST` 改为 `status.HTTP_400_BAD_REQUEST`。

**验收标准**：
- 对应分支触发时返回 400，不出现属性错误。

---

## 阶段 B：性能与稳定性优化（P1）

### B1. 知识库上传改流式处理
**涉及文件**：
- `jushi_backend/app/api/v1/endpoints/knowledge.py`

**实施要点**：
1. 分块读取上传流并累计大小。
2. 超限立即终止并返回 413/400（按约定）。
3. 按需写临时文件后原子落盘。

**验收标准**：
- 大文件上传内存占用显著下降；
- 超限时可提前失败。

---

### B2. 重建索引异步化
**涉及文件**：
- `jushi_backend/app/api/v1/endpoints/knowledge.py`
- `jushi_backend/app/services/rag_service.py`

**实施要点**：
1. 将 rebuild 操作移至后台执行（线程池/任务队列）。
2. 接口返回任务 ID 或状态信息。
3. 增加任务状态查询与失败日志。

**验收标准**：
- 重建期间 API 主链路响应时间稳定；
- 可追踪任务成功/失败。

---

### B3. Mongo 连接策略按环境分离
**涉及文件**：
- `jushi_backend/app/database.py`
- `jushi_backend/app/core/config.py`

**实施要点**：
1. 本地开发可保留轻量配置；生产移除 `directConnection=True`。
2. 补齐 pool、超时、健康检查参数。
3. 连接失败日志脱敏且可定位。

**验收标准**：
- 本地/生产连接参数可配置；
- 故障时错误可观测。

---

## 阶段 C：架构收敛（P1）

### C1. Chat 业务拆分
**涉及文件**：
- `jushi_backend/app/business/chat_business.py`
- 新增或重构相关 service 模块

**实施要点**：
1. 拆出“路由决策/执行器/持久化/响应组装”。
2. 逐步迁移，保持对外接口不变。
3. 每步迁移后补充回归测试。

**验收标准**：
- 核心流程可读性显著提升；
- 关键路径具备独立可测性。

---

### C2. Web API 单一业务入口
**涉及文件**：
- `jushi_agent/src/app/api/**`
- `jushi_agent/src/lib/api/proxy.ts`

**实施要点**：
1. 核心业务统一下沉到 `jushi_backend`。
2. Next API route 仅做轻量代理/BFF。
3. 下线重复业务实现路径。

**验收标准**：
- 同一业务规则只存在单一来源；
- 调试路径清晰。

---

## 阶段 D：工程治理（P2）

### D1. 拆分巨型页面与组件
**涉及文件**：
- `mobile/jushi_mobile/app/(tabs)/index.tsx`
- `mobile/jushi_mobile/app/(tabs)/schedule.tsx`
- `jushi_agent/src/components/chat/ChatInterface.tsx`

**实施要点**：
- 抽离子组件、hooks、状态容器；
- 明确 UI 层与数据层边界。

**验收标准**：
- 单文件复杂度下降，变更影响范围收敛。

---

### D2. 依赖与构建治理
**涉及文件**：
- `jushi_agent/package.json`
- `.gitignore`

**实施要点**：
1. 清理未使用依赖，类型包归位 `devDependencies`。
2. 清理 `.next_stale_*` 等历史产物并补充忽略规则。

**验收标准**：
- 安装与构建更轻量；
- 仓库无陈旧构建噪音。

---

### D3. 配置可移植性与文档对齐
**涉及文件**：
- `mobile/jushi_mobile/app.json`
- `README.md`
- `jushi_backend/README.md`

**实施要点**：
1. 移除本机绝对路径与固定隧道地址，改环境注入。
2. 更新 README 与当前架构保持一致。

**验收标准**：
- 新机器可按文档直接运行；
- 文档与实际模块一致。

---

## 建议执行顺序（可直接排期）
1. 阶段 A（全部）
2. 阶段 B（B1→B2→B3）
3. 阶段 C（C2→C1，先统一入口再拆核心）
4. 阶段 D（并行推进）

---
