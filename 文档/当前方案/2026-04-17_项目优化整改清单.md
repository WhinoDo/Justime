# 项目优化整改清单（P0 / P1 / P2）

> 日期：2026-04-17  
> 作用：用于统一跟踪本项目的优化项优先级与执行顺序，便于排期与任务分配。

---

## P0（必须优先完成）

### 1) 修复校验常量错误（运行时正确性）
- 文件：`jushi_backend/app/core/validators.py:112`
- 问题：使用了 `status.HTTP_400_REQUEST`（错误常量）。
- 目标：替换为 `status.HTTP_400_BAD_REQUEST`。
- 验收：相关校验分支触发时不再抛常量错误。

### 2) 去除不安全默认密钥（安全）
- 文件：
  - `jushi_backend/app/services/encryption_service.py:20`
  - `jushi_backend/app/core/config.py:76`
- 问题：`JWT_SECRET` 缺失时存在默认不安全回退值。
- 目标：
  - 启动时强制校验必填密钥；
  - 加密密钥与 JWT 签名密钥职责分离。
- 验收：密钥缺失时服务直接失败并给出明确提示。

### 3) 强化认证 Cookie 策略（安全）
- 文件：`jushi_backend/app/api/v1/endpoints/auth.py:40,81`
- 问题：Cookie 未统一启用生产安全属性。
- 目标：统一 `httponly / samesite / secure / path` 策略（生产启用 `secure=True`）。
- 验收：登录/刷新/登出行为一致，生产 Cookie 满足安全要求。

### 4) 修复客户端传 userId 的权限边界问题（安全）
- 文件：
  - `jushi_agent/src/app/api/calendar/events/route.ts:18`
  - `jushi_agent/src/app/api/calendar/events/[id]/route.ts:20,70,106`
- 问题：服务端信任客户端传入 `userId`，存在越权风险。
- 目标：用户身份仅来自服务端鉴权上下文，资源操作必须带 owner 约束。
- 验收：跨用户资源访问/修改被拒绝。

### 5) 统一错误返回规范（API 一致性）
- 文件：`jushi_backend/app/api/v1/endpoints/knowledge.py`（多个 `try/except` 分支）
- 问题：混用 HTTPException 与 `200 + {success:false}`。
- 目标：按语义返回标准 HTTP 状态码，并统一错误结构。
- 验收：前端可稳定按状态码与结构处理错误。

## P1（高收益优化）

### 6) 拆分 Chat 大型业务流程（可维护性）
- 文件：`jushi_backend/app/business/chat_business.py:880-1485`
- 问题：单方法承载过多职责，改动风险高。
- 目标：拆分为路由决策、执行、持久化、响应组装等模块。
- 验收：主流程收敛，关键路径可独立测试。

### 7) 上传改流式处理（性能/稳定性）
- 文件：`jushi_backend/app/api/v1/endpoints/knowledge.py:81`
- 问题：一次性 `await file.read()` 易造成内存峰值。
- 目标：按块读取并在超限时提前终止。
- 验收：大文件并发上传时内存压力可控。

### 8) 索引重建改后台任务（吞吐）
- 文件：`jushi_backend/app/api/v1/endpoints/knowledge.py:208`
- 问题：请求内执行重任务会阻塞。
- 目标：改后台任务/线程池执行，接口快速返回任务状态。
- 验收：重建期间 API 主链路响应不受显著影响。

### 9) 优化 Mongo 连接参数（生产可用性）
- 文件：`jushi_backend/app/database.py:26`
- 问题：`directConnection=True` 不利于副本集/故障切换场景。
- 目标：分环境配置连接策略，生产移除该参数并补充池化/超时设置。
- 验收：本地与生产连接行为可预期，故障恢复更稳。

### 10) 收敛 Web API 架构（架构一致性）
- 文件：
  - `jushi_agent/src/lib/api/proxy.ts:12`
  - `jushi_agent/src/app/api/calendar/events/route.ts:8`
  - `jushi_agent/src/app/api/documents/route.ts:8`
- 问题：代理模式与直连数据库模式并存。
- 目标：核心业务统一走后端服务，前端仅保留 BFF/代理。
- 验收：同一业务规则仅保留单一实现来源。
