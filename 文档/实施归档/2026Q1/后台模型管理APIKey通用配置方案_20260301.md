# 后台模型管理API Key通用配置方案

> **文件作用**: 为管理后台添加通用的 API Key 管理功能，支持自定义命名的 API Key 并在模型配置中统一引用。
> **创建时间**: 2026-03-01 15:50

---

## 1. 目标分析

**用户诉求**：
在后台管理的模型管理页面，添加一个通用的 API Key 添加方式。管理员可以选择添加一个自命名的 API Key（例如 "DeepSeek 官方 Key"、"千问主账号 Key"），然后在模型配置中引用它来为指定模型添加 API Key，避免同一个 Key 在多个模型配置中重复手填。

**核心改动点**：
1. **新建 API Key 管理模块**：在数据库新增 `system_api_keys` 集合，实现增删改查后台与前端页面。
2. **改造现有模型配置**：允许模型配置（`system_llm_configs`）绑定/引用 `api_key_id`。
3. **平滑渲染 API Key**：在系统实际拉取模型列表（`UserService.get_system_llm_configs()`）时，自动根据 `api_key_id` 注入真实的 API Key，使得核心的对话调用层（`agent_service.py` 等）完全无感知。

---

## 2. 后端实施计划

### 2.1 新增 API Key 数据模型与业务逻辑
- **新建 `jushi_backend/app/models/admin_apikey.py`**：定义 `AdminApiKey` (id, name, api_key, updated_at) 和 `AdminApiKeyUpsertRequest` Schema。
- **新建 `jushi_backend/app/business/admin_apikey_business.py`**：封装对 MongoDB `system_api_keys` 的 CRUD。所有存入数据库的 API Key 均需要通过 `encryption_service.encrypt()` 加密。

### 2.2 新增 API Key 后台接口
- **新建 `jushi_backend/app/api/v1/endpoints/admin_apikeys.py`**，提供四个管理接口：
  - `GET /admin/apikeys`
  - `POST /admin/apikeys`
  - `PUT /admin/apikeys/{key_id}`
  - `DELETE /admin/apikeys/{key_id}`
- 在 `jushi_backend/app/api/v1/api.py` 中注册该路由器。

### 2.3 改造 `system_llm_configs` 数据结构及存取逻辑
- **改造 `jushi_backend/app/models/admin.py`**：
  - 在 `AdminModel` 和 `AdminModelUpsertRequest` 中增加可选字段 `api_key_id: Optional[str] = None`。
- **改造 `jushi_backend/app/business/admin_business.py`**：
  - 在 `_build_model_doc` 等写入逻辑中支持接收和保存 `api_key_id`。
- **改造核心获取逻辑 `UserService.get_system_llm_configs`** (`jushi_backend/app/services/user_service.py`)：
  - 加载 `system_llm_configs` 列表后，提取所有包含 `api_key_id` 的模型。
  - 从 `system_api_keys` 中聚合或单独查询对应的加密 API Key，覆盖到模型对象的 `api_key` 字段中返回，保障调用层的逻辑零修改。

## 3. 前端界面实施计划

### 3.1 增加「API Key 管理」路由与菜单
- **修改 `src/app/admin/layout.tsx`**：在左侧菜单项 `menuItems` 中新增 `{ title: 'API Key 管理', icon: Key, href: '/admin/apikeys' }`。
- **新建 `/admin/apikeys/page.tsx`**：复用模型管理的极简暗色毛玻璃 UI 风格，实现 API Key 列表的展示与增删改弹窗操作。出于安全考虑，列表不展示 key 的明文，仅展示名称和更新时间。

### 3.2 改造「模型管理」创建/编辑弹窗
- **修改 `/admin/models/page.tsx`**：
  - 在页面加载时，并行请求 `/api/admin/apikeys` 获取可选的 API Key 列表。
  - 将原本的“API Key文本输入框”调整为 Select 选项或包含「引用现有密钥」和「自定义独立密钥」的组合输入方式：
    - 提供一个 Select 供选择：可以选择已添加在 `system_api_keys` 中的通用 Key（传递 `api_key_id`），也可以选择“手动输入”。
    - 如果选择“手动输入”，展示原有的 `api_key` 输入框；如果选择“通用 Key”，则隐藏输入框并只提交 `api_key_id`。

## 4. 验证计划 (Verification Plan)

### 4.1 手工验证测试
1. **密钥创建验证**：
   - 作为 admin 登录进入后台 -> 点击“密钥管理”。
   - 新增一个测试密钥如 `Test DeepSeek Key: sk-xxxx`，确认列表渲染且数据库 `system_api_keys` 成功写入且加密。
2. **模型绑定验证**：
   - 切换到模型管理，编辑或新增一个模型。
   - 在 API Key 字段下来选择刚创建的 `Test DeepSeek Key`。
   - 提交并在 MongoDB `system_llm_configs` 查看该模型配置，确认保存了 `api_key_id`，而没有保存独立的 `api_key`。
3. **对话链路验证**：
   - 回到前端用户对话窗口，选择刚刚配置了通用 Key 的模型发起对话。
   - 观察后端日志 `UserService.get_system_llm_configs` 是否成功将其替换为真实的 API Key，且大模型调用成功返回 (HTTP 200)。
