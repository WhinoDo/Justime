# 聚时项目 - 全局路由鉴权与统一重定向改造方案

## 1. 改造目标
当前系统架构中，部分页面（如 `dashboard`）在客户端判定未登录后会发生 URL 级别的重定向（跳转到 `/auth`），而部分页面（如 `chat`、`admin/*`）则保留原始 URL 但仅仅渲染一个报错或拦截组件。

为了统一用户体验闭环且提高页面的防闪烁（FOUC）能力，本方案引入 **Next.js 服务端中间件（Middleware）** 方案。
- **未授权访问保护路由**：服务器会直接劫持请求，发生 `307 Temporary Redirect` 强制跳往 `/auth?mode=login`，并携带原访问地址（`redirect` 参数）。
- **客户端净化**：去除由于服务端已拦截而变得冗余的客户端拦截展示 UI。

---

## 2. 新增核心文件：全局中间件

**路径：** 新增 `justime_agent/src/middleware.ts` 
*(注意：Next.js App Router 的 middleware 通常放在 `src/` 目录下，与 `app/` 平级)*

**代码实现指引：**
创建一个 `middleware.ts` 文件，核心逻辑是通过检查客户端携带的 `access_token` Cookie（由后端签发并存储的令牌）来判断登录状态。

```typescript
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

// 定义需要登录才能访问的受保护路由前缀
const protectedRoutes = [
  '/dashboard',
  '/chat',
  '/admin',
  '/profile',
  '/knowledge',
  '/calendar',
  '/model-config'
]

// 定义仅限未登录用户访问的路由（如登录页）
const publicOnlyRoutes = ['/auth']

export function middleware(request: NextRequest) {
  const { pathname, searchParams } = request.nextUrl
  
  // 1. 获取认证 Token (聚时系统使用的是 access_token)
  const token = request.cookies.get('access_token')?.value
  const isAuthenticated = !!token

  // 2. 检查是否在访问受保护路由
  const isProtectedRoute = protectedRoutes.some(route => 
    pathname === route || pathname.startsWith(`${route}/`)
  )

  // 3. 检查是否在访问仅限未登录用户的路由
  const isPublicOnlyRoute = publicOnlyRoutes.some(route => 
    pathname === route || pathname.startsWith(`${route}/`)
  )

  // 场景 A：未登录且访问了受保护的页面 -> 重定向到登录页，并带上回跳地址
  if (!isAuthenticated && isProtectedRoute) {
    const redirectUrl = new URL('/auth', request.url)
    redirectUrl.searchParams.set('mode', 'login')
    // 保存尝试访问的页面路径，以便登录后跳回
    redirectUrl.searchParams.set('redirect', pathname + request.nextUrl.search)
    return NextResponse.redirect(redirectUrl)
  }

  // 场景 B：已登录却访问了 Auth 登录页 -> 重定向到主大盘
  if (isAuthenticated && isPublicOnlyRoute) {
    // 优先尝试获取 URL 上的 redirect 参数，如果没有则回 dashboard
    const redirectPath = searchParams.get('redirect') || '/dashboard'
    return NextResponse.redirect(new URL(redirectPath, request.url))
  }

  // 其他情况放行
  return NextResponse.next()
}

// 匹配器配置：决定哪些路径触发 Middleware
export const config = {
  matcher: [
    /*
     * 匹配所有的请求路径，除了以下几种：
     * - api (API routes)
     * - _next/static (static files)
     * - _next/image (image optimization files)
     * - favicon.ico, sitemap.xml, robots.txt (meta files)
     * - images, svg, etc (public files)
     */
    '/((?!api|_next/static|_next/image|favicon.ico|images|.*\\.png$).*)',
  ],
}
```

## 3. 客户端代码净化 (Client Refactoring)

中间件接入后，未经授权的用户**永远无法到达受保护组件的渲染阶段**。因此，我们需要清理以前为补救未授权而产生的客户端 UI 代码。

### 3.1 改造 `src/app/chat/page.tsx`
- **原逻辑**：存在一大段 `if (!isAuthenticated || !user)` 返回 "Login Required" 的 JSX 代码。
- **修改为**：直接删除这段退场 UI。只需保留 `isLoading` 时期的骨架/缓冲屏，随后默认用户必然已登录。

### 3.2 改造 `src/app/admin/layout.tsx`
- **说明**：后台稍微有些特殊，由于中间件只能判断“是否登录”（token 存在与否），至于用户“是否为 admin” 属于角色校验，一般在进入大门后的组件内验证逻辑（如果不做服务端鉴权中心的话）。
- **修改为**：保留当前的 `if (!user || user.role !== 'admin')` 这个红盾牌 "访问被拒绝" 的鉴权组件。但您可以放心地去掉因“未登录”而导致的闪烁或者白屏。

### 3.3 改造 `src/app/dashboard/page.tsx`
- **原逻辑**：存在 `if (!isLoading && !isAuthenticated) { router.push('/auth?mode=login&redirect=/dashboard') }`。
- **修改为**：删除这个 `useEffect` 重定向代码块，因为当页面走到这一步时，浏览器早就在访问 URL 的网络阶段被服务器 Middleware 以 307 劫持到了 auth 页，根本不会执行这里的客户端跳转，删除可减少代码冗余。
