# 修复 RAG 检索回答与引用片段不对应的问题

## 🐛 深入现象与根因分析

你遇到的**“问的问题能答出来，但下面引用的片段文不对题”**，本质上是由于 LlamaIndex 的默认切块策略与本地中文 Embedding 模型参数不匹配，以及后端返回片段被暴力截断的“连环案”造成的：

1. **Embedding 上限与块切分冲突 (默默丢失检索视⻆)**
   默认情况下，`LlamaIndex` 在建立索引时，会把文档切分成大小为 **1024** 的 Chunk。但是，咱们本地运行的 `BAAI/bge-base-zh-v1.5` 模型的最大上下文长度其实只有 **512 Tokens**！这就导致：当一段 1024 长度的文本送去计算向量时，后半段的 512 个字被**直接默默丢掉（截断）**了。如果答案刚好在后半段，检索不仅可能匹配偏离，还会导致引用极度不精准。

2. **前端传回的 Snippet 被暴力截断了**
   如果仔细看 `rag_service.py` 中的 `_extract_reference_from_node` 方法：
   ```python
   snippet = " ".join(content.split())[:500]
   ```
   它强制只取了文本块的**前 500 个字符**作为气泡下方的“片段内容”抛给前端！如果这个 Chunk 的正确匹配内容刚好在第 600 个字，LLM 看原文本能答对，但前端显示的引用片段早就在 500 字处被腰斩了，所以你看起来就会觉得“文不对题”。

## 🛠️ 给 Codex 的修复修改指南

为了彻底让检索和引用严丝合缝，请按照以下步骤同时修改 `rag_service.py`，然后重新构建索引：

### 1. 修改 `justime_backend/app/services/rag_service.py`

#### A. 配置合理的 Chunk Size (第 140 行附近)
找到 `_configure_llamaindex_settings` 方法内部的末尾，添加两行以将切割粒度缩小，紧紧贴合中文 BGE 模型的 512 上限（设置 300 保证安全），增加一点重叠率防止上下文断裂：

```python
def _configure_llamaindex_settings() -> None:
    # ... 省略原有代码 ...
    
    # [新增] 限制 LlamaIndex 全局的文档切块大小与重叠度
    # bge-base-zh-v1.5 最大支持 512 Tokens，这里切到 300 左右可以保证每段文本都能被完整向量化，且引用颗粒度更精准。
    Settings.chunk_size = 300
    Settings.chunk_overlap = 30
    
    # LLM 使用运行时动态加载...
    Settings.llm = None
```

#### B. 改进 Snippet 截断逻辑 (第 353 行附近)
找到 `_extract_reference_from_node` 方法底部的这段代码，把 `[:500]` 的暴力截断干掉，改成保留整个 Chunk 内容（因为我们已经把 Chunk 缩小到了 300 字，完全不需要再次截断）：

**把原来的：**
```python
        snippet = " ".join(content.split())[:500]
        if not snippet:
            return None
```
**修改为：**
```python
        # 直接使用全部切割好的 chunk 内容，因为它本身已经被缩小到了 chunk_size (300)
        snippet = " ".join(content.split())
        if not snippet:
            return None
```

### 2. 重新扫描生成索引库

代码修改完后，旧的拥有“错误大号 Chunk”的缓存必须要清空。
请你在终端里重新干掉一遍缓存并重启后端：

1. `rm -rf app/data/storage` （在 `justime_backend` 目录下）
2. 重新执行 `python start.py` 启动

这样重启后，你的 `串.pdf` 将会被切分成数百个 300 字的精准小块，并且你在前端看到的气泡引用必定就是严丝合缝的那块文字！快让 Codex 执行吧！
