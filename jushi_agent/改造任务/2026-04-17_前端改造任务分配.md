# 前端改造任务分配

> 日期：2026-04-17  
> 作用：基于《项目优化落地改造方案》，拆分前端可执行任务并分配责任范围。

---

## 目标范围（前端）
- 收敛前端 API 架构：统一走后端服务，减少重复业务逻辑。
- 修复权限边界：前端不再传 `userId` 作为可信身份。
- 提升可维护性：拆分超大组件/页面，统一请求层。
- 工程治理：依赖清理、环境配置去硬编码。

---

## 任务分配

## FE-1：接口与权限边界改造（优先级 P0）
**负责人建议**：前端主程  
**涉及文件**：
- `src/app/api/calendar/events/route.ts`
- `src/app/api/calendar/events/[id]/route.ts`
- `src/app/api/documents/route.ts`
- `src/app/calendar/page.tsx`
- `src/components/document/DocumentEditor.tsx`

**改造内容**：
1. 清理客户端显式传 `userId` 的请求参数。
2. 接口调用改为依赖服务端鉴权上下文。
3. 对资源 ID 操作接口补齐 owner 约束配合（与后端联调）。

**验收标准**：
- 前端请求不再携带可伪造用户身份字段。
- 跨用户数据访问在前后端联调中被正确拒绝。

---

## FE-2：API 架构收敛（优先级 P1）
**负责人建议**：前端架构负责人  
**涉及文件**：
- `src/lib/api/proxy.ts`
- `src/app/api/**`（重点 calendar/documents/chat 相关）

**改造内容**：
1. 明确“前端仅代理/BFF，核心业务逻辑在 backend”的边界。
2. 清理直接数据库式的 API route 逻辑。
3. 统一错误映射与响应结构处理（配合后端统一错误契约）。

**验收标准**：
- 同一业务规则仅有一处实现来源（后端）。
- 前端 API 层具备统一调用与错误处理行为。

---

## FE-3：聊天与日程大组件拆分（优先级 P2）
**负责人建议**：两名前端并行

**任务 A（Web）涉及文件**：
- `src/components/chat/ChatInterface.tsx`

**任务 B（Mobile）涉及文件**：
- `mobile/jushi_mobile/app/(tabs)/index.tsx`
- `mobile/jushi_mobile/app/(tabs)/schedule.tsx`

**改造内容**：
1. 将 UI、状态管理、请求调用分离为子组件 + hooks。
2. 降低单文件复杂度，减少不必要重渲染。

**验收标准**：
- 单文件职责清晰，关键逻辑可定位。
- 主要交互流程（发消息、查看日程）行为与改造前一致。

---

## FE-4：移动端配置去硬编码（优先级 P1）
**负责人建议**：移动端负责人  
**涉及文件**：
- `mobile/jushi_mobile/app.json`
- `mobile/jushi_mobile/scripts/start-backend-and-expo.js`
- `mobile/jushi_mobile/context/AuthContext.tsx`（如需适配）

**改造内容**：
1. 移除本机路径 `javaHome`、固定 ngrok 地址。
2. 改为环境变量或本地覆盖配置。
3. 保证新机器可按文档直接运行。

**验收标准**：
- 本地/测试环境通过配置切换 API 地址。
- 无开发者机器强绑定路径。

---

## FE-5：依赖治理与工程卫生（优先级 P2）
**负责人建议**：前端工程化负责人  
**涉及文件**：
- `package.json`
- `.gitignore`
- 历史构建残留目录

**改造内容**：
1. 清理未使用依赖（如 Prisma/NextAuth/Supabase 等需逐项确认）。
2. `@types/*` 放入 `devDependencies`。
3. 清理 `.next_stale_*` 产物并完善忽略规则。

**验收标准**：
- 安装与构建依赖更精简。
- 仓库中不再出现历史构建噪音。

---

## 联调与发布顺序建议
1. **先 FE-1 + 后端鉴权改造联调**（P0）
2. 再做 FE-2（API 架构收敛）
3. 并行推进 FE-4（移动端配置）
4. 最后 FE-3、FE-5（维护性与治理）

---

## 风险提示
- FE-1/FE-2 与后端改造强依赖，建议同一迭代推进。
- 大组件拆分期间需防 UI 回归，建议每次拆分后做最小可用验证。
